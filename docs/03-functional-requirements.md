# FieldOps — Functional Requirements

## Document Status

Initial MVP requirements based on project discovery. Business assumptions are not yet validated with real users.

## FR-01 — Register Service Request

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow an authenticated administrator to register a customer service request.

### Required Information

- Customer name
- Customer phone number
- Service location/address
- Service type (installation, repair, or maintenance)
- Problem or service description

### Optional Information

- Request source (phone, WhatsApp, walk-in, etc.)
- Preferred service date
- Priority

### Acceptance Criteria

**AC-01:** Given an authenticated administrator, when valid required information is submitted, the system creates a service request.

**AC-02:** Given a request with missing required information, when the administrator submits it, the system rejects the submission and identifies the invalid fields.

**AC-03:** When a service request is successfully created, the system assigns it a unique reference number.

**AC-04:** A newly registered service request has an initial status of `PENDING_REVIEW`.

**AC-05:** A technician cannot register service requests.

**AC-06:** When a request is created successfully, the system records the creation timestamp and the administrator who registered it.

### Business Rules

- Only administrators may register service requests.
- Every registered request must have a unique reference.
- A newly registered request must await administrative review before approval.
- Invalid submissions must not create a service request.

### Open Questions

- Should email be accepted instead of a phone number?
- Can a service location be approximate?
- Can the service type be marked as unknown until assessment?

These questions are unresolved and should not be treated as validated business requirements.

## FR-02 — Generate Unique Service Request Reference

**Priority:** Must Have

**Actor:** System

**Description:**

The system must automatically generate a unique reference number for every successfully registered service request.

### Acceptance Criteria

**AC-01:** Every successfully registered request receives an automatically generated reference number.

**AC-02:** No two registered service requests may have the same reference number.

**AC-03:** Concurrent request registrations must produce different reference numbers.

**AC-04:** Administrators cannot manually select or modify request reference numbers.

**AC-05:** The reference number is visible when viewing the service request.

**AC-06:** A request's reference number remains unchanged throughout its lifecycle.

### Business Rules

- Each registered request must have exactly one unique reference number.
- References are generated by the system.
- References must never be reused for different requests.
- References remain unchanged after creation.

### Open Design Decision

The reference format and generation strategy will be decided during system design.

## FR-03 — View and Filter Service Requests

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow authenticated administrators to view registered service requests, filter them by status, and open individual requests to view their details.

### Acceptance Criteria

**AC-01:** An authenticated administrator can view all registered service requests.

**AC-02:** Each request displays its reference number, customer name, service type, current status, and registration date.

**AC-03:** Administrators can filter requests by `PENDING_REVIEW`, `APPROVED`, or `DECLINED`.

**AC-04:** When a status filter is applied, only matching requests are displayed.

**AC-05:** Administrators can clear the filter to view all requests.

**AC-06:** Administrators can open an individual request to view its details.

**AC-07:** When no requests match a filter, the system displays an appropriate empty-state message.

**AC-08:** Technicians cannot access the administrator's full service request list.

### Business Rules

- Only administrators can access the full service request list.
- Declined requests remain accessible for tracking and accountability.
- Filtering must not modify stored request information.
- Technicians can access relevant customer information only through their assigned work orders.

### Scope Notes

- Filtering by status is required for the MVP.
- Searching by reference number or customer name is optional.
- Advanced analytics and reporting are deferred

## FR-04 — Approve or Decline Service Requests

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow an authenticated administrator to review a service request in `PENDING_REVIEW` status and either approve or decline it.

Declining a request requires a reason. The system must preserve the request and record the decision.

### Acceptance Criteria

**AC-01:** When an administrator approves a request in `PENDING_REVIEW`, its status changes to `APPROVED`.

**AC-02:** When an administrator declines a request in `PENDING_REVIEW` with a valid reason, its status changes to `DECLINED`.

**AC-03:** Declining a request without a meaningful reason is rejected, and the request status remains unchanged.

**AC-04:** Every approval or decline records the administrator responsible, the decision timestamp, and the status change.

**AC-05:** Declined requests remain accessible to administrators, including their decline reasons and decision histories.

**AC-06:** Technicians cannot approve or decline requests.

**AC-07:** Requests that are no longer in `PENDING_REVIEW` cannot undergo the normal initial review decision again.

**AC-08:** Declined requests cannot be used to create work orders.

### Business Rules

- Only administrators may approve or decline requests.
- Only requests in `PENDING_REVIEW` may undergo initial review.
- Declining requires a meaningful reason.
- Approved requests become eligible for work-order creation.
- Declined requests must remain stored.
- Every review decision must record the responsible administrator and timestamp.
- Repeated submissions must not create duplicate or conflicting decisions.

### Open Questions

- Should approval require a reason?
- Can declined requests be reopened?
- Can approved requests be cancelled?
- How should accidental review decisions be corrected?

These questions will be revisited during domain modelling.

## FR-05 — Create Work Order from Approved Request

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow an authenticated administrator to create a work order from an approved service request.

Each work order must be linked to its originating service request. For the MVP, each service request may have at most one work order.

A work order may exist without an assigned technician.

### Acceptance Criteria

**AC-01:** An administrator can create a work order from an `APPROVED` service request that does not already have one.

**AC-02:** The system rejects work-order creation from requests in `PENDING_REVIEW` or `DECLINED`.

**AC-03:** Repeated creation attempts for the same approved request must not create duplicate work orders.

**AC-04:** The system records the originating service request, creation timestamp, and administrator responsible.

**AC-05:** A newly created work order may remain unassigned.

**AC-06:** An administrator can view the work order linked to a service request.

**AC-07:** Technicians cannot create work orders.

**AC-08:** Concurrent creation attempts for the same service request must result in at most one work order.

### Business Rules

- Only administrators may create work orders.
- Work orders can be created only from approved service requests.
- Each work order must belong to exactly one service request.
- Each service request may have at most one work order in the MVP.
- Creating a work order and assigning a technician are separate actions.
- The system must prevent duplicate work orders.

### Open Questions

- Should work orders have their own reference numbers?
- What should the initial work-order status be?
- Should administrators add job instructions during creation?
- Can work orders be cancelled?
- How should multiple site visits be handled?

These questions will be reviewed during domain modelling.

## FR-06 — Assign Technician to Work Order

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow an authenticated administrator to assign one active technician to an existing work order.

A work order may remain unassigned until a technician is selected.

### Acceptance Criteria

**AC-01:** An administrator can assign an active technician to an unassigned work order.

**AC-02:** The system rejects assignment to an inactive technician and leaves the existing assignment unchanged.

**AC-03:** A work order can remain unassigned without being deleted.

**AC-04:** A work order must have no more than one currently assigned technician.

**AC-05:** When an assignment succeeds, the system records the technician, the administrator responsible, and the assignment timestamp.

**AC-06:** An administrator can view the assigned technician or see that the work order is unassigned.

**AC-07:** Technicians cannot assign work orders to themselves or other technicians.

**AC-08:** An assigned technician can access the work order through their assigned-work list.

**AC-09:** Important assignment changes are preserved in the work-order history.

### Business Rules

- Only administrators may assign technicians.
- Only active technicians may receive new assignments.
- A work order may exist without an assigned technician.
- Each work order may have at most one currently assigned technician.
- Assignment changes must record the responsible administrator and timestamp.
- Assignment permissions must be enforced on the backend.

### Open Questions

- Can administrators reassign jobs after work has started?
- Can an administrator remove an assignment without replacing the technician?
- What happens if an assigned technician becomes inactive?
- Should previously assigned technicians retain read-only access?
- Should the system detect scheduling conflicts?

Scheduling conflict detection is outside the initial MVP.

## FR-07 — View Assigned Work Orders

**Priority:** Must Have

**Actor:** Technician

**Description:**

The system must allow authenticated technicians to view only the work orders currently assigned to them.

Administrators must be able to view all work orders, including unassigned work orders.

### Acceptance Criteria

**AC-01:** An authenticated technician can view a list containing only their currently assigned work orders.

**AC-02:** Each listed work order displays its reference, service type, customer name, service location, and current status.

**AC-03:** A technician can open a work order assigned to them and view the details needed to perform the job.

**AC-04:** A technician cannot access a work order assigned to another technician, even by entering its URL directly.

**AC-05:** A technician cannot access an unassigned work order.

**AC-06:** An administrator can view all work orders, including assigned and unassigned work orders.

**AC-07:** When a technician has no assigned work orders, the system displays an appropriate empty-state message.

**AC-08:** When a work order is reassigned, the previously assigned technician loses access through the normal technician interface.

**AC-09:** Unauthenticated users cannot access protected work-order information.

### Business Rules

- Technicians may access only work orders currently assigned to them.
- Administrators may access all work orders.
- Access restrictions must be enforced on the backend.
- Knowing a work-order reference does not grant access.
- Reassignment must update access permissions.
- Technicians must not receive unrelated customer information.

### Open Questions

- Should technicians retain read-only access to previously assigned jobs?
- Which customer contact details should technicians see?
- Should technicians see work-order history from before their assignment?
- Should closed work orders remain visible to the technician who completed them?

For the initial MVP, technician access is based on current assignment

## FR-08 — Update Work-Order Progress

**Priority:** Must Have

**Actor:** Technician

**Description:**

The system must allow an authenticated technician to update the progress of a work order currently assigned to them, following permitted status transitions.

The system must reject unauthorized or invalid status changes and record successful progress updates.

### Proposed Work-Order States

- `UNASSIGNED` — The work order has no assigned technician.
- `ASSIGNED` — A technician has been assigned but has not started work.
- `IN_PROGRESS` — The assigned technician has started work.
- `COMPLETION_SUBMITTED` — The technician has submitted the job for administrative review.
- `CLOSED` — An administrator has formally closed the work order.

### Acceptance Criteria

**AC-01:** Given an authenticated technician assigned to a work order in `ASSIGNED` status, when they start the job, its status changes to `IN_PROGRESS`.

**AC-02:** A technician cannot start a work order that is not currently assigned to them.

**AC-03:** A technician cannot change the status of a work order assigned to another technician.

**AC-04:** The system rejects invalid status transitions, such as changing directly from `ASSIGNED` to `CLOSED`.

**AC-05:** When a valid progress update succeeds, the system records the previous status, new status, responsible technician, and timestamp.

**AC-06:** A rejected status change leaves the work-order status unchanged.

**AC-07:** A technician cannot directly change a work order to `CLOSED`.

**AC-08:** A work order in `UNASSIGNED` status cannot be started until an active technician is assigned.

**AC-09:** A technician cannot submit completion directly from `ASSIGNED`; the work order must first reach `IN_PROGRESS`.

### Business Rules

- Only the currently assigned technician may start or update the execution progress of a work order.
- Work-order status changes must follow permitted transitions.
- Starting work changes the status from `ASSIGNED` to `IN_PROGRESS`.
- Submitting completion is a separate action governed by FR-09.
- Closing a work order is an administrator action governed by FR-10.
- Every successful status transition must record the responsible user and timestamp.
- Invalid transitions must not modify the work order.

### Open Questions

- Can a technician pause a job that is in progress?
- What happens when a job cannot be completed during the first visit?
- Can an administrator return a submitted completion report for correction?
- What happens if a technician is reassigned after starting work?
- Can a closed work order be reopened?

These exception workflows will be reviewed during Day 2 domain modelling.

## FR-09 — Submit Job Completion

**Priority:** Must Have

**Actor:** Technician

**Description:**

The system must allow the currently assigned technician to submit a work order for administrative review after completing the required work.

The technician must provide meaningful completion notes describing the work performed. Completion photos are optional.

A successful submission changes the work-order status from `IN_PROGRESS` to `COMPLETION_SUBMITTED`.

### Acceptance Criteria

**AC-01:** Given an authenticated technician assigned to a work order in `IN_PROGRESS`, when they submit valid completion notes, the system changes the status to `COMPLETION_SUBMITTED`.

**AC-02:** When completion notes are missing, empty, or contain only whitespace, the system rejects the submission.

**AC-03:** When a completion submission is rejected, the work-order status remains unchanged.

**AC-04:** A technician cannot submit completion for a work order assigned to another technician.

**AC-05:** A technician cannot submit completion for an unassigned work order.

**AC-06:** A technician cannot submit completion directly from `ASSIGNED` or `UNASSIGNED` status.

**AC-07:** When completion is submitted successfully, the system records the completion notes, responsible technician, and submission timestamp.

**AC-08:** Completion photos are not required for a successful submission.

**AC-09:** A successful completion submission does not automatically close the work order.

**AC-10:** An administrator can view the submitted completion notes when reviewing the work order.

### Business Rules

- Only the currently assigned technician may submit job completion.
- A work order must be in `IN_PROGRESS` before completion can be submitted.
- Completion notes are mandatory.
- Notes containing only whitespace are invalid.
- Completion photos are optional and may be deferred from the MVP.
- A successful submission changes the status to `COMPLETION_SUBMITTED`.
- Every successful submission records the responsible technician and timestamp.
- Only an administrator may formally close a completed work order.
- Repeated submissions must not create duplicate completion records.

### Open Questions

- What level of detail is required for completion notes?
- Should the technician record materials used?
- Should the technician record time spent on the job?
- Can a technician edit completion notes after submission?
- Can an administrator reject a completion report and return the job to the technician?
- Should customers confirm that work was completed?

These questions will be reviewed during domain modelling.

## FR-10 — Review and Close Work Order

**Priority:** Must Have

**Actor:** Administrator

**Description:**

The system must allow an authenticated administrator to review the completion information submitted by a technician and formally close a work order.

Only work orders in `COMPLETION_SUBMITTED` status may be closed through the normal closure workflow.

### Acceptance Criteria

**AC-01:** Given an authenticated administrator and a work order in `COMPLETION_SUBMITTED`, when the administrator opens the work order, the system displays the submitted completion notes, responsible technician, and submission timestamp.

**AC-02:** Given a work order in `COMPLETION_SUBMITTED`, when an administrator approves its completion, the work-order status changes to `CLOSED`.

**AC-03:** When a work order is closed, the system records the administrator responsible and the closure timestamp.

**AC-04:** An administrator cannot close a work order that is in `UNASSIGNED`, `ASSIGNED`, or `IN_PROGRESS` status.

**AC-05:** A technician cannot formally close a work order.

**AC-06:** When a work order is closed, its completion notes and important status history remain accessible to administrators.

**AC-07:** A repeated closure attempt must not create duplicate closure records or change the original closure timestamp.

**AC-08:** When an unauthorized user attempts to close a work order, the system rejects the action without changing its status.

### Business Rules

- Only administrators may formally close work orders.
- A work order must be in `COMPLETION_SUBMITTED` before it can be closed.
- The administrator must be able to review submitted completion information.
- Closing a work order changes its status to `CLOSED`.
- Every successful closure must record the responsible administrator and timestamp.
- Closing a work order must not delete its completion notes or history.
- Repeated closure attempts must not produce duplicate closure events.
- A closed work order cannot undergo normal technician progress updates.

### Open Questions

- Can an administrator reject a completion report and return the work order to `IN_PROGRESS`?
- Should an administrator provide closure notes?
- Should a customer confirm satisfactory completion?
- Can a closed work order be reopened?
- Should administrators be required to provide a reason when reopening a job?

These exception workflows will be reviewed during Day 2 domain modelling.

## FR-11 — Record Important Changes and Audit History

**Priority:** Must Have

**Actor:** System

**Description:**

The system must automatically record important service request and work-order events so authorized users can understand what happened, when it happened, and who was responsible.

Audit history must preserve relevant previous and new values for changes such as status transitions and technician assignments.

### Events to Record

- Service request registration.
- Service request approval or decline.
- Work-order creation.
- Technician assignment and reassignment.
- Work-order progress changes.
- Job completion submission.
- Work-order closure.

### Acceptance Criteria

**AC-01:** When a service request is created, the system records the creation event, responsible administrator, and timestamp.

**AC-02:** When a request is approved or declined, the system records the decision, responsible administrator, timestamp, and previous and new statuses.

**AC-03:** When a work order is created, the system records its creation event and originating service request.

**AC-04:** When a technician is assigned or reassigned, the system records the responsible administrator, timestamp, previous technician (if any), and new technician.

**AC-05:** When a work-order status changes, the system records the previous status, new status, responsible user, and timestamp.

**AC-06:** When job completion is submitted, the system records the submitting technician and submission timestamp.

**AC-07:** When a work order is closed, the system records the closing administrator and closure timestamp.

**AC-08:** An administrator can view the history of important events associated with a service request or work order.

**AC-09:** Technicians cannot modify or delete audit history records.

**AC-10:** Rejected actions must not create misleading records indicating that the attempted business action succeeded.

### Business Rules

- Important business events must be recorded automatically.
- Audit records must identify the action, responsible user, and timestamp.
- Status and assignment changes must preserve relevant previous and new values.
- Ordinary users cannot edit or delete audit records through the application.
- Audit history must remain accessible to authorized administrators.
- A successful business change and its required audit record must be saved consistently.
- Audit history must not be silently overwritten when a record changes.

### Open Questions

- Should technicians see the history of their assigned work orders?
- How long should audit records be retained?
- Should administrators be allowed to export audit history?
- Should failed access attempts be recorded separately in security logs?
- How should audit history handle deleted or deactivated user accounts?

These questions will be reviewed during domain modelling and security design.

## FR-12 — Attach Optional Completion Photos

**Priority:** Should Have (Optional — Post-Core MVP)

**Actor:** Technician

**Description:**

The system should allow a technician to attach photos to a work order as supporting evidence of completed work.

Completion photos are optional. A technician must still be able to submit valid completion notes without uploading any photos.

This feature will be implemented only if the core MVP requirements are completed and tested within the available development time.

### Acceptance Criteria

**AC-01:** An authenticated technician can upload completion photos only to a work order currently assigned to them.

**AC-02:** The system accepts supported image formats, such as JPEG and PNG.

**AC-03:** The system rejects unsupported file formats and files exceeding a configured size limit.

**AC-04:** Successfully uploaded photos are associated with the correct work order.

**AC-05:** An administrator can view completion photos attached to a work order.

**AC-06:** A technician can submit completion notes without uploading any photos.

**AC-07:** A technician cannot access or upload photos for another technician's work order.

**AC-08:** Uploaded photos are not publicly accessible without authorization.

**AC-09:** If a photo upload fails, the system displays an error without incorrectly marking the upload as successful.

### Business Rules

- Completion photos are optional.
- Completion notes remain mandatory under FR-09.
- Only the currently assigned technician may upload photos to an eligible work order.
- Administrators may view photos associated with work orders.
- File type and size must be validated on the backend.
- Access to stored photos must be restricted to authorized users.
- Photo uploads must not be required to close a work order.
- The feature must not delay delivery of Must Have requirements.

### Open Questions

- What is the maximum number of photos per work order?
- What is the maximum allowed file size?
- Should technicians upload photos before or during completion submission?
- Can technicians remove photos after submitting completion?
- Where should photos be stored?
- How long should completion photos be retained?

These decisions can be made when the optional photo feature is implemented.
